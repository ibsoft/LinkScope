# Endpoint Protection — release candidate

Keep Microsoft Defender enabled. Monitor mode is the default. Install the current supported Windows ClamAV release separately from https://www.clamav.net/downloads. LinkScope does not bundle ClamAV or its signature databases.

## Setup
The updated `LinkScopeSetup.exe` can install a verified local ClamAV MSI and automatically provision or repair the standard Windows services, definitions and loopback configuration. See [CLAMAV-SETUP.md](CLAMAV-SETUP.md). The following manual steps remain useful for custom installations.
1. Install ClamAV in a directory writable only by trusted administrators. Follow the vendor instructions to create `clamd.conf` and `freshclam.conf` from the shipped examples; remove the Example directive. Use the same `DatabaseDirectory` in both configurations.
2. In clamd.conf set `TCPAddr 127.0.0.1`, `TCPSocket 3310`, `StreamMaxLength 25M` (or larger), and `AlertExceedsMax yes`. Do not expose this unauthenticated TCP service to the LAN. Restrict its service account and database directory ACLs. Keep unsigned bytecode disabled. Start clamd after downloading official databases with freshclam.
3. Schedule `freshclam.exe` using its supported daemon or Windows Task Scheduler configuration, under a dedicated restricted account. Set `NotifyClamd` to the absolute clamd.conf path if supported by your installed version, or reload/restart clamd after updates. Use the vendor's recommended update cadence. Verify `clamd` VERSION and PING.
4. In LinkScope Settings > Endpoint Protection, enable monitoring and enter local protected paths, exact excluded directories/files, interval, bulk-change threshold and local port. Save and open Endpoint Protection > Scan now. Event Viewer output is optional (existing Unixfor LinkScope source, event 4201).

## Third-party signatures (opt-in)
FreshClam supports repeated `DatabaseCustomURL` directives in its host-local configuration. Use only administrator-approved HTTPS URLs, from a trusted provider, with a known supported content or hash database extension such as `.ndb`, `.ldb`, `.hdb`, `.hsb`. Add the directives manually on the host (not through the LinkScope web UI), for example:

```
# Replace these illustrative URLs with actual verified provider URLs.
# DatabaseCustomURL https://your-approved-signature-provider.example/custom.ndb
# DatabaseCustomURL https://your-approved-signature-provider.example/custom.hdb
TestDatabases yes
```

No third-party source is enabled by default. Review the provider's licensing, authenticity and update policy, verify a detached signature or independently published digest where available, and test in staging before use. HTTPS alone does not authenticate the publisher of a database beyond the server's TLS identity. Avoid unsigned bytecode, ignore/allowlist databases and untrusted rules. Restrict updater outbound traffic to approved destinations. Third-party signature downloads and reload are performed by FreshClam, not LinkScope; its update log is independent of LinkScope. The dashboard displays the version response from clamd, not a verified per-feed signature age. For isolated hosts use an approved offline database distribution process. See https://docs.clamav.net/manual/Usage/SignatureManagement.html and https://docs.clamav.net/manual/Installing/Community-projects.html.

## Expanded endpoint implementation
Use **Monitor** first. The application remains disabled by default. New settings include real-time watching, 10–600 second behavior window, 1–100 MiB per-file scan cap (match ClamD `StreamMaxLength`), exact exclusions and case-insensitive filename wildcards, existing canary paths, response mode, explicit response scopes, exact eligible executable paths and a pinned ClamD binary. Both modes that modify the host require a verified `clamd.exe` under Program Files and its SHA-256 from a trusted installation (`Get-FileHash -Algorithm SHA256 -LiteralPath ...`). The connection's actual TCP peer owner is checked against the pinned binary for automatic actions. Re-pin after a verified engine upgrade. Do not permit untrusted users to modify the engine, configuration, databases or signature feeds. Keep ClamD on IPv4 loopback only.

- **Monitor**: detection, persistent evidence, no removal or process action. Real-time `FileSystemWatcher` queues changes; bounded incremental full scans reconcile missed events. Watcher/queue overflow opens a coverage incident. Files locked, reparse-linked, over the size cap, or rejected by ClamAV are not considered verified. Scan throughput depends on I/O and engine latency; this is not pre-write interception.
- **Canaries**: create benign, known-good files in monitored directories before first enabling the policy. An existing file is enrolled on first successful observation, with its original hash stored separately in SQLite. Content changes/deletion raise a critical incident; scans do not replace the baseline. Reverting the original content resolves the finding. Use a new explicitly configured canary path for deliberate replacement. Do not enroll files on a compromised host. Canary content that exceeds the scan cap or cannot be read is a coverage warning. Canary rechecks are queued every ten seconds; backlog may delay observation.
- **Behavior**: persisted SHA-256 and first-64-KiB Shannon entropy samples detect content changes across service restarts and completed scans; exact paths and policy scope affect baseline. Distinct changed paths in the configured sliding window produce warnings. A bulk change combined with multiple high-entropy increases can raise a critical *suspected* ransomware incident. Compression, backups, and legitimate updates may look similar. This is heuristic and does not prove encryption or ransomware. The sliding activity window itself is in memory and resets on restart. Changing protected paths/exclusions creates a new comparison scope; old canary hashes are retained.
- **Process evidence**: enable Windows Advanced Audit Policy > Object Access > Audit File System (Success), then configure a write/delete SACL on the selected test files or folders. Grant the LinkScope service account the minimum necessary Security log read permission (for example, Event Log Readers plus the required channel ACL on your OS); restart the service after changing token group membership. Verify event 4663 exists. LinkScope queries up to 512 recent events within 30 seconds and matches the exact file path and write/delete access mask. The event provides executable path/PID; correlation is not certain attribution and may be unavailable or ambiguous. It is not ETW or kernel write interception. No audit policy, SACL or service privileges are automatically changed.
- **Protect**: only a confirmed non-heuristic ClamAV signature within an explicitly configured non-system response scope is eligible. A stable handle, canonical final path, single link, matching SHA-256 and independent re-scan are required. Windows/program files/ProgramData/LinkScope paths, drive roots, reparse points, hard links, inaccessible or changing files are refused. DPAPI machine-bound sealed bytes and metadata are written into the restricted vault before the original is marked for deletion using the same verified handle. A failed removal leaves evidence and a warning. No web download or executable restore is exposed. Vault quota: 2 GiB and fewer than 1,000 entries. Inspect quota and evidence regularly; no automatic deletion.
- **Contain**: includes Protect and a strictly restricted process termination attempt. Requires a fresh canary violation or critical bulk/entropy incident, recent matching Security event, exact eligible EXE path, confirmed non-heuristic ClamAV finding on the process image file, trusted ClamD peer, process-handle identity/start time verification, noncritical process and nonzero session. Response fails closed when these checks or required Windows privileges fail. A disk executable signature does not prove what code is loaded in memory; fileless/unknown threats and service/session-zero processes are not automatically stopped. There is no broad process termination or network isolation. Never enable in production before an explicit change review and isolated testing.

### Signature updates
FreshClam still owns the official and opt-in third-party updates. `Update-LinkScopeSignatures.ps1` is a local maintenance helper for a trusted installed updater and config; it requires HTTPS custom URLs with `.ndb/.ldb/.hdb/.hsb` and `TestDatabases yes`. Run it from an approved Windows scheduled task or use FreshClam's native supported schedule. Example: `powershell.exe -NoProfile -File Update-LinkScopeSignatures.ps1 -FreshClamExe "C:\Program Files\ClamAV\freshclam.exe" -ConfigFile "C:\Program Files\ClamAV\freshclam.conf"`. Keep provider credentials and logs restricted; approve provider licensing, integrity, HTTPS origins and signatures independently. The script does not verify third-party publisher signatures itself. FreshClam and its installed version determine actual validation/reload. The dashboard displays the ClamD VERSION-reported database version/date and warns when a parseable date is older than three days (approximate local timestamp); per-provider freshness is not verified. The web application does not accept feed URLs or updater executable downloads. Do not enable automatic response until third-party feeds are tested for false positives.

### Persistent evidence and reporting
`%ProgramData%\LinkScope\data\endpoint\endpoint.sqlite` contains file state, trusted canaries, findings, incident history and a durable alert outbox. The central alerts database commits its endpoint delivery cursor with each alert batch to avoid duplicate replay. The outbox is drained in batches; even short-lived findings or incidents beyond the dashboard cap reach central alert history, subject to successful delivery. Dashboard/API show latest 200 active details, 100 historical incidents, 100 quarantine metadata rows, and pending delivery count; central Alert History has its normal retention/search. The endpoint database and quarantine vault do not participate in ordinary cleanup; plan storage/backup and review retention separately. Logs/Toastr/bell/email/JSON/Syslog/SIEM follow existing settings and receiver availability; Event Viewer is optional, event 4201. The PDF report includes an endpoint summary and full collected endpoint snapshot when enabled. API `endpoint_protection` requires scoped tokens. AI and telemetry consume the same bounded evidence. The master Windows DPAPI protection and sealed bytes are not exposed by these endpoints.

### Local evidence recovery
Run `Export-LinkScopeQuarantine.ps1` only as an elevated incident responder, on the original Windows host, into an existing restricted and isolated review directory. Supply the evidence ID shown in the dashboard, and explicitly confirm export. It decrypts the DPAPI blob, verifies SHA-256, creates a new `.bin` without overwrite and appends a local recovery audit JSONL. It does not restore original paths or ACLs/alternate streams, execute the file, or automatically delete evidence. Use independent review and trusted backups for production restoration. Local recovery audit is a separate host-local record (not the web User Audit database). Quarantine protects file content, not all NTFS metadata. Treat the vault and database as sensitive; local admin/SYSTEM compromise can still bypass or alter local monitoring. Retain independent backups and remote SIEM evidence.

### Deployment gate
Rebuild with Visual Studio (.NET Framework 4.8 x64) or `Build.cmd` (all embedded resources synchronized with the project). `LinkScope.exe --self-test` includes added safe endpoint tests; execute them on Windows. Test monitoring, canaries, exclusions, stale/unavailable engine, mock benign bulk changes, alert outbox recovery, reports, API, and the standard EICAR test with approved permissions. Use a disposable VM for any quarantine or termination test. Do not enable Protect/Contain before those tests pass. This source revision is a release candidate, not a certified production antivirus. Keep Defender and backups enabled.
