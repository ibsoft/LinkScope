# LinkScope Endpoint Protection V29 — source release candidate

## Scope and policy

Only endpoint-protection behavior, its UI, and regression tests were changed. The original setup already enrolls the pre-elevation installing user's profile SID (not LocalService or SYSTEM) and adds the resolved local profile path on first installation. Existing custom application paths, exclusions, response policy, canary baselines and databases are preserved. Add more fixed local directories in Settings > Endpoint Protection > Protected paths, for example `D:\Applications` or `C:\unx`. The profile remains the installing user's profile, not a dynamically switching set of all interactive users. Additional user profiles and redirected locations must be enrolled separately. Upgrade does not override intentional removal or disabled policies. Default mode is Monitor (detection only); automatic response requires explicitly restricted response paths and a trusted engine pin. No change to Windows folder ACLs, service identities, or primary antivirus.

## Changes

* Local FileSystemWatcher error callbacks now invalidate the specific watcher instance. The worker disposes/re-registers it and can fall back to the existing independently refreshed privileged watcher and journal. The endpoint page displays coverage per configured root: local watcher, SYSTEM watcher, journal, initializing, excluded or uncovered.
* Actual journal gaps schedule immediate reconciliation (or another pass after the current pass); routine directory notifications remain coalesced at the normal interval. Reconciliation does not erase malware evidence based on an incomplete scan.
* Selected watcher work is persisted into the existing bounded SQLite queue before attempting file scanning. A failed scan is no longer acknowledged merely because in-memory retries were exhausted. Failed entries remain pending with retry deferral; capacity exhaustion is explicitly an overflow/reconciliation event. Events not yet selected from the memory queue remain subject to event loss on a crash; NTFS replay and full reconciliation are the recovery mechanisms.
* In standard Windows service mode, ClamD TCP ownership is checked against the SCM registered running clamd process before sending local file bytes or trusting version output. The SYSTEM reader retains its stronger image/path verification. Ordinary file handles are checked against the requested final path before reading. Missing paths under restricted service access are confirmed by the scoped SYSTEM reader where supported. No new privileged operation or pipe command is introduced.
* The scanner accepts exact `stream: OK` and valid INSTREAM signature findings, not arbitrary success suffixes. Transport failure opens a pause on ordinary scans until the engine reconnects, with a 15-second engine health retry cadence. Scans are not marked clean after an incomplete verdict. This is not a guarantee of native ClamD throughput or availability. The existing 30-second per-command network deadline and 45-second privileged reply deadline remain.
* Endpoint UI reports degraded coverage, unverified signature freshness and pending work; per-folder coverage is not a claim that every file has been scanned. Existing setup profile defaults are retained. The source archive deliberately excludes supplied old executable/build outputs, which would otherwise mask changes.

## Build and installation

Extract to a clean directory on Windows. Use Visual Studio with .NET Framework 4.8 Developer Pack and the existing x64 solution. Close previous setup executables before rebuilding. Run `Rebuild-VisualStudio.cmd Release` (or `Build-VisualStudio.cmd Release`) from the extracted root. Use the resulting `bin\Release\LinkScopeSetup.exe`, not any previous installer. Run the wizard normally from the intended Windows user account and allow elevation. Upgrade both services, retain existing settings/data, and verify `Get-Service LinkScope,LinkScopeUsn,clamd,freshclam`. Review the original setup logs if installation fails. Back up `C:\ProgramData\LinkScope` using an administrator-controlled method before upgrading; do not delete the live database or reset canary baselines to conceal findings.

## Windows acceptance gate (not executed here)

1. Fresh install under a non-administrator interactive user and elevate with separate administrator credentials; verify only the intended profile is enrolled by default. Upgrade an existing configured profile plus a custom folder; verify both remain and a deliberately disabled policy stays disabled.
2. Verify each root's actual watcher status and ClamD version/signature freshness. Temporarily stop the helper and check fallback coverage or explicit degraded state; restart it and observe recovery. Rename/remove a disposable custom folder and recreate it; verify fault reporting and re-registration. Do not remove a live profile to test.
3. Run elevated `LinkScope.exe --endpoint-engine-self-test`, and use `--endpoint-scan-file <absolute path>` to inspect a benign file. In an isolated test VM with permission, test an official EICAR test file (primary antivirus may intercept it first). Test Downloads, Documents, AppData and a custom application directory. Verify true verdicts and persisted incident history.
4. Stop ClamD during a scan in a test VM; verify no clean verdict, pending retries and scanner pause. Restart ClamD; verify reconnection and retry. Restart LinkScope while failed work is queued; verify persisted work survives. Exercise locked files, missing files, duplicate events, oversized files and excluded paths.
5. Run the existing native self-test and `tests\Verify-SourceBuild.ps1 -FullBuild` from Developer PowerShell, check Windows event log and application telemetry, validate resource consumption and sustained scan throughput with a realistic profile. Test monitor vs explicit protect response separately, with disposable data.

## Release limitations

This is post-event, user-mode detection, not a filesystem minifilter, pre-execution blocking or a replacement for Microsoft Defender/enterprise EDR. Reparse targets, locked files, file-size cap (100 MiB default), finite traversal and queue limits, and restricted SYSTEM directory enumeration limits can leave partial coverage. Monitor mode does not quarantine. The original setup's profile discovery and background exclusions are unchanged. Existing broader UI test issues are not addressed. No Windows native compile, installation, service/IPC/ClamD execution or performance/load/security acceptance was possible in the Linux environment. Do not label as production-certified until those gates pass. See ENDPOINT-TEST-RESULTS.txt for executed portable checks.
