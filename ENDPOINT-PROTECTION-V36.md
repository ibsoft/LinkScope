# LinkScope Endpoint Protection V36 — Incremental baseline and recovery

Release candidate. Built from the V35 source archive. Windows/.NET Framework 4.8 compilation, installation, actual ClamAV scans and production benchmarks have not been performed in this environment.

## Behavior

* Scheduled/manual baseline traversal reads and SHA-256 hashes every eligible file from a verified file handle. It can reuse a previous **clean** ClamAV verdict only if the hash, path, complete LinkScope endpoint policy, verified engine generation and age match, no active finding exists for the file, the engine is online, and authorization remains valid. It does not trust modification timestamps as a content identity. Cache hits do not extend expiration, increment the fresh scan counter, or clear active threat findings. Maximum age is seven days from the original fresh verdict.
* The cache uses a separate SQLite table; old file hashes in V35 are not treated as antivirus verdicts. Successful baseline INSTREAM scans may populate it only if the verified engine generation matches immediately before and after the scan. Real-time files, downloads and canaries still get fresh scans. Missing/changed files, failed verdicts, non-clean verdicts, expired entries and policy mismatches cannot reuse an old clean verdict. Real-time fresh scans invalidate the old path entry. There are no new file exclusions.
* Cache support is deliberately limited to the standard local Windows-service ClamD installation on port 3310. The generation includes the actual VERSION response from the verified peer, registered process ID and start time, checked process image, clamd.conf hash and trusted standard definition file metadata. Unsupported configurations, unrecognized/third-party definition files, lack of process/ACL access, and uncertain main/bytecode reload state disable caching rather than bypassing scanning. Custom signature scanning itself remains available. The optimization adds generation verification overhead; benchmark it on the target host before claiming a speed improvement. A local privileged administrator can modify the host and is outside this cache's threat model.
* LinkScope-initiated database updates, observed FreshClam log updates and observed live VERSION changes invalidate cached verdicts and request a new baseline. A new ClamD process identity cannot match an old generation. Cache is pruned before a baseline (age and row count).
* The privileged helper has a new scoped baseline operation (mode 4); it independently validates the saved local policy, verified final path/handle, content hash and live engine generation. The main worker also validates the reply against its own cached candidate. The original scan, download and watcher operations are preserved. Upgrade both services together.
* Baseline traversal uses persistent SQLite frontier/visited/state tables. Each completed traversal step transactionally advances the frontier after scan evidence is written. A crash before commit leaves the step available for replay. A resumed baseline is not declared authoritative: it schedules a follow-up reconciliation pass, retaining existing security findings and coverage warnings. Changed policy discards the old frontier. Existing 100,000-path baseline cap, size caps, reparse boundaries and file-lock handling remain in effect.
* New configurations default to 86400 seconds between baseline attempts. Saved intervals are preserved; to adopt daily scanning on an existing installation set Settings > Endpoint Protection > Baseline reconciliation interval (seconds) = 86400 with real-time monitoring enabled. Directory notifications and lost provider coverage may request earlier reconciliation (at most the previous 300-second interval when idle). Journal gaps, manual requests and signature updates can trigger sooner. Telemetry freshness is independent of the baseline interval. A shorter interval is advisable if real-time monitoring is disabled.
* Dashboard separates fresh clean checks and cached clean verifications, displays cached files in the baseline and reports resumed traversal. Reset & rescan clears cache and checkpoint without erasing threats. Endpoint history reset also clears the cache/frontier, preserving active security evidence, quarantine, canaries and pending durable real-time work as in V35.

## Windows acceptance procedure

1. Back up the existing service configuration and endpoint database. Extract to a clean directory, run `Rebuild-VisualStudio.cmd Release`, install the newly built setup and confirm both LinkScope and LinkScopeUsn are upgraded. Hard refresh the local dashboard.
2. In an isolated test folder enrolled in Endpoint Protection, create several benign files; verify first baseline fresh verdicts. Run Scan now again before signatures change; expect cached clean verifications if all cache-generation guards are satisfied. If none appear, verify standard ClamD installation, access to engine/configuration and definition set; do not weaken ACLs to force caching.
3. Modify a file while preserving its prior timestamp. Verify a fresh verdict for the changed content. Copy or rename a file and verify fresh real-time inspection. Test a locked file and a file above the size limit; neither may show cached clean. Canary integrity checks must remain independent.
4. In a test VM use the existing benign EICAR antivirus test procedure; verify detection (not a cached clean verdict), then confirm settings reset preserves active findings. Do not use live malware.
5. Interrupt a large baseline by restarting LinkScope while keeping ClamD running. Verify the resumed checkpoint and subsequent reconciliation pass. Restart ClamD and verify previous generation cannot be reused. Update signatures and verify another baseline is requested. Check that the next baseline uses new verdicts; older cache entries must not be used.
6. Run Reset & rescan and verify cache counters reset and fresh baseline verdicts. Verify Endpoint history reset with confirmation clears old history without removing quarantine or other modules.
7. Benchmark a representative profile and application tree: baseline completion time, file-read I/O, CPU/RAM, ClamD timeouts, cache hit rate and latency from new file arrival to fresh verdict. Test watcher overflow, service restart and disabled/misconfigured helper. Approve only after results satisfy your requirements.

## Validation and limitations

See `ENDPOINT-TEST-RESULTS-V36.txt`. Selected portable tests exercise actual SQLite statements, rollback and restart, source wiring and existing browser fixtures. They are not native service tests. Two selected regression scripts fail: signature settings roundtrip (ProfileDefaultsApplied) and an endpoint activity DOM mock that lacks querySelectorAll. Existing scan limits, journal historical path resolution, unavailable process attribution, locked files and post-event detection remain limitations. The optimization reads all eligible files during a baseline; it is not metadata-only NTFS incremental traversal. It does not implement a filesystem minifilter, pre-execution blocking or automatic permission modifications.
