# Endpoint Protection V33 — scoped history reset

## Changes

Settings → Endpoint Protection → Endpoint history reset → Reset endpoint history. The existing Reset & rescan action on the Endpoint Protection dashboard remains non-destructive. The new action requires an administrator session, a valid CSRF token, a destructive confirmation dialog, and an exact server-side confirmation value. It is not a generic database reset. An accepted request is queued to the existing endpoint worker. The UI displays queued/running/completed/failed status rather than claiming the operation completed when queued. Save or discard any outstanding Settings edits before requesting the reset.

The reset logically deletes Endpoint Protection scan activity, incident history, resolved findings, ordinary per-path operational coverage records, completed diagnostic file probes, and ordinary file observation history. The central alert database removes only Endpoint Protection alert records, corresponding search-index entries and pending mail jobs. The global alert sequence is not reset. Other categories are unaffected. Current active security findings and associated file evidence are retained and republished; unresolved journal gaps and overflow evidence are retained. The protected scope, exclusions, response policy, enrolled canary hashes, quarantine payloads and receipts, signature maintenance state, pending real-time/USN work and journal checkpoints are preserved. No protected files are deleted. Windows Event Logs, application logs, administrative audit records, backup copies and externally delivered SIEM/email events are not purged. An SMTP delivery already in flight cannot be recalled. This is logical database deletion, not a forensic secure erase.

A local transaction inserts a reset-pending marker and prepares the retained findings for republication. The separate central alert database is then cleaned in its own transaction. The marker is cleared after successful central cleanup. The endpoint worker will resume a partially completed two-database reset after a service restart and will not publish pre-reset transitions while this stage has failed. A request still queued only in worker memory at the moment of a service crash can be lost; resubmit if it was never processed. The operation has no cross-database atomic commit. Active findings can generate new notification records, and new scans start producing fresh records immediately. A failure is visible in the service log; partially completed cleanup is retried when the persisted marker exists. The new baseline starts when the enabled scanner next runs; completion of reset does not imply completion of baseline or full coverage.

## Scan cap and current report

The supplied 23:02 report confirms a saved 25 MiB per-file limit and 26 outstanding size-limit entries (including a 44,836,536-byte installer). Existing administrative settings are deliberately not silently overwritten. Settings now documents the recommended 100 MiB cap for the standard LinkScope ClamD configuration (StreamMaxLength 100M, MaxFileSize 100M, MaxScanSize 200M). Verify the actual installed engine settings first, then save the updated cap. ClamAV decompression/scan limits still apply. The 2.9 GB ISO will remain outside the supported per-file cap and must not be reported clean. Do not segment arbitrary files and treat individual chunks as a complete malware verdict. No blanket exclusions were added.

Baseline traversal is still in memory and restarts on a service restart or policy change; durable baseline checkpointing is not implemented in V33. Eight unresolved journal records were reported in the supplied snapshot. Their protected-scope membership is unknown; the warning is not suppressed or treated as resolved by the new reset. A successful complete baseline and appropriate journal reconciliation are still required. The source does not establish that every previously reported locked or oversized file has been inspected. This is post-event monitoring, not pre-execution blocking.
