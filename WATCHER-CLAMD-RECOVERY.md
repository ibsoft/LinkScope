# V28 — Watcher heartbeat and ClamD transport recovery

The privileged metadata watcher runs independently of the scanner on its own background thread. A successful response is fresh for 30 seconds; first registration receives at most 15 seconds of initialization grace. Pending initialization is not marked as verified coverage. Failed registrations report their stage, and real coverage gaps remain warnings. Old scope responses cannot update the new policy. The privileged helper remains bound to its exact saved local scope; no folder ACL or service identity changes are made.

The ClamD client previously imposed a five-second receive timeout despite a nominal thirty-second scan deadline. The new async loopback client uses a two-second connect cap, a five-second control-command budget and a thirty-second total signature-scan network budget, including sending the stream and waiting for a verdict. It closes timed-out connections and checks cancellation during pending network I/O. Local file reads and peer validation are not hard-real-time operations. It distinguishes incomplete engine verdicts from file access failures. No failed verdict is marked clean. Failed journal scans are deferred for 30 seconds in SQLite and remain queued; acknowledgement clears the deferral. Canary hash checks and genuine findings are retained. The scan loop can still be delayed by slow filesystem I/O and ClamD work; the watcher heartbeat no longer depends on that loop.

## Windows acceptance checks

Upgrade both LinkScope services and confirm `Get-Service LinkScope,LinkScopeUsn,clamd`. Confirm the configured profile is shown, and the privileged watcher status becomes active (or gives a concrete stage-specific error). Run the existing elevated `LinkScope.exe --endpoint-engine-self-test` and `LinkScope.exe --endpoint-scan-file <absolute path>` commands. Test a new EICAR download and a copied test file. If the engine still times out, inspect `C:\ProgramData\LinkScope\ClamAV\clamd.log` if present (otherwise consult the LogFile setting in clamd.conf); inspect the ClamD process and its listening port. Never count a PING response alone as a malware verdict. Do not delete the database or existing canaries.

Portable source and SQLite tests are provided; no Windows build, native watcher or ClamD runtime tests were executed in the development environment.
